# REST INFO — план веб-версии (отдельная ветка)

Обновлено: 2026-09-23

## Зафиксированные решения (23.09.2026)

| Вопрос | Выбор |
|--------|--------|
| Сессия в браузере | **httpOnly cookie** — `/auth/login-web`, `/auth/register-web`, `/auth/logout-web`; Electron по-прежнему Bearer |
| Объём v1 | **Паритет с десктопом** (общий UI из `app/src`) |
| URL API | **Поле на экране входа** (localStorage) |
| Админка | **Полная**, как SettingsPage |

## Цель

Параллельный **браузерный** клиент к тому же PostgreSQL/API: часть пользователей — десктоп (Electron), часть — веб. Десктоп **не ломаем** и **не меняем в процессе разработки**, пока веб не готов к выкладке.

## Принципы (изоляция)

| Правило | Как |
|--------|-----|
| Код десктопа не трогаем | Вся работа в ветке `feature/web`; каталог **`web/`** — новый пакет, `app/` и `server/src` на `main` без правок |
| Сервер «как есть» | Текущие REST-эндпоинты уже достаточны для чтения/правки; **новых миграций под веб не планируем** на первом этапе |
| Без офлайна | Нет локального JSON, `pending-operations`, full/incremental sync в UI |
| Медиа | Только URL с API (`GET /media/...`); подгрузка **при открытии темы** (lazy), без локального кэша как у Electron |
| Данные на экране | Всегда с сервера: список тем + одна тема по запросу; после save — refetch |
| Обновления | Статика на nginx/CDN; пользователю не нужен Setup |

**Исключение на production (только в день выкладки веба, не в коде десктопа):** nginx — location для SPA + `CORS_ORIGIN` на домен веба (см. ниже). Electron на это не опирается.

## Git-ветка

```text
main          — только десктоп + стабильный сервер (как сейчас)
feature/web   — долгоживущая ветка; периодически merge/rebase main → feature/web (подтягивать фиксы API)
web-v1.0.0    — тег релиза SPA, когда готово
```

- **Не мержить** `feature/web` в `main`, пока нет решения «включаем веб в production».
- PR в `main` с веба — только добавление `web/` + доки + опциональный nginx-фрагмент; **без рефакторинга** `app/electron/*`.

## Архитектура

```text
                    ┌─────────────────┐
                    │  PostgreSQL     │
                    └────────┬────────┘
                             │
                    ┌────────▼────────┐
                    │  Express API    │  (без изменений логики)
                    │  auth, topics,  │
                    │  media, admin   │
                    └────────┬────────┘
              ┌──────────────┼──────────────┐
              │              │              │
     ┌────────▼────────┐     │     ┌────────▼────────┐
     │ Electron app/   │     │     │ web/ (Vite SPA) │
     │ IPC + локальный │     │     │ fetch + JWT     │
     │ кэш + sync      │     │     │ без sync        │
     └─────────────────┘     │     └─────────────────┘
```

### Слой доступа к данным

Сейчас UI завязан на `window.spravochnik.*` (preload → main → `server-api.ts`).

В **`web/`** — свой тонкий клиент:

- `web/src/api/` — `fetch` к тем же URL, что уже дергает Electron (auth, departments, topics, media, admin по роли).
- JWT: `Authorization: Bearer` после `POST /auth/login` (как сейчас на сервере).
- Хранение сессии: см. раздел «Безопасность» (cookie vs localStorage).

Компоненты UI **не копировать слепо**: постепенно переносить или вынести общее в `packages/shared` **только на ветке web**, когда появится второй потребитель — на `main` shared не обязателен до merge.

## MVP → полная версия (фазы)

### Фаза 0 — каркас (1–2 дня)

- [ ] Ветка `feature/web`, `web/package.json` (Vite, React 19, TS, те же major, что `app/`).
- [ ] Env: `VITE_API_BASE` (production URL API).
- [ ] Экран входа (email/password, URL сервера **фиксирован** в build или один инпут только для dev).
- [ ] Health + login + logout.

### Фаза 1 — чтение (MVP для «сидеть в веб»)

- [ ] Список отделов / фильтры party (как у читателя).
- [ ] Дерево тем: `GET` данных отдела (аналог payload после sync, но **один запрос** — либо существующий sync full один раз при смене отдела, либо отдельный aggregate-эндпоинт **только если** окажется слишком тяжёлым; предпочтение — **не менять API**, использовать `GET /sync/changes?since=0` или текущие topics list routes — уточнить по факту на ветке).
- [ ] Просмотр темы: markdown, ссылки между темами (SPA routing `#/dept/topicId`).
- [ ] Медиа в markdown: src → `/media/...` с токеном или cookie (как уже отдаёт API).

**Не в MVP:** reorder, topic locks UI, offline, настройки «Синхронизировать с диском», electron-updater.

### Фаза 2 — редактирование (паритет с редактором, без reorder)

- [ ] Topic lock через API (как десктоп).
- [ ] CRUD тем, upload медиа через `POST /media`, лимиты как на сервере.
- [ ] Роли: editor — свой отдел; admin/owner — по текущим правилам API.

### Фаза 3 — админка (опционально)

- [ ] Подмножество SettingsPage: пользователи, whitelist, storage-stats — только если нужно в браузере; иначе «админ — только десктоп».

### Фаза 4 — production

- [ ] Сборка `web/dist`, nginx `try_files` + кэш статики.
- [ ] `CORS_ORIGIN=https://справочник.example.ru` (уже поддерживается в `server/src/index.ts`).
- [ ] CSP, HTTPS-only, отдельный поддомен (`app.` / `web.`).

## Что сознательно **не** переносим в веб v1

- Очередь офлайн-операций, конфликты sync side-by-side (нет локальной копии).
- Авто-pull каждые 60 с — достаточно refetch при фокусе вкладки / после save (опционально лёгкий polling `GET /sync/status`).
- Reorder с drag-and-drop (можно v2 или только десктоп).
- Журнал сессии Electron, windowBounds, установщик Setup.
- Яндекс / legacy storage.

## Влияние на работающую систему

| Компонент | Изменения на `main` до релиза веба |
|-----------|-------------------------------------|
| `app/` | **0** |
| `server/` код | **0** (CORS уже есть) |
| Production DB | **0** |
| nginx | Только новый `location` для SPA при выкладке (файл в `docs/` или `nginx/web.conf.example` на ветке web) |
| Десктоп-пользователи | Без изменений |

## Безопасность (главный минус веба)

Риски выше, чем у Electron: XSS → кража JWT, CSRF (если cookie), утечка через DevTools, общий ПК.

**Меры в плане:**

1. **HTTPS** обязательно; HSTS на nginx.
2. **CSP** (строгий `script-src`, без inline где возможно).
3. **Токен:** предпочтительно **httpOnly Secure SameSite=Strict cookie** (потребует небольшого расширения auth на сервере — делать **только на ветке web** + feature-flag или отдельный `POST /auth/login-web`; не ломать текущий JSON `{ token }` для Electron). Альтернатива MVP — `sessionStorage` + короткий TTL JWT (хуже, но без правок auth).
4. **Rate limit** login (nginx `limit_req` или middleware — только при выкладке веба).
5. **Не** хранить пароли в localStorage; не логировать токены в analytics.
6. Аудит: admin/owner действия уже на сервере; для веба — тот же JWT и те же `requireRole`.
7. Регулярные обновления зависимостей `web/` (отдельный lockfile).

Десктоп остаётся «толще» локально, но attack surface браузера — публичный URL.

## Плюсы (зафиксировано)

- Нет установки и переустановки Setup; деплой = замена `dist/`.
- Новый сотрудник — ссылка + логин.
- Один backend, одни данные, десктоп и веб одновременно.

## Оценка сложности

| | |
|--|--|
| Изоляция от десктопа | **Простая** — отдельная ветка + каталог `web/` |
| UI-паритет | **Средняя** — много логики в `App.tsx` + IPC; переподключение к fetch |
| Сервер | **Минимальная** — auth cookie (желательно) + nginx |
| Срок до MVP «только чтение» | порядка **1–2 недель** при фокусе |
| Срок до редактирования | **+2–4 недели** (locks, медиа, роли) |
